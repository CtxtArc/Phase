# PHASE in 15 minutes

PHASE checks the part of hardware code that C can't: *who owns a buffer
right now* — the CPU, a DMA engine, a device — and whether every line of
the program respects that. You describe the coordination in PHASE; the
number crunching stays in C. If the compiler accepts your program, the
CPU never touches a buffer the hardware owns, never frees one the hardware
is writing into, never skips a protocol step, and never misuses a
hardware register.

This tutorial builds up from one buffer to a circular DMA stream, a
packet protocol, a board's register maps and interrupts. Every program is in
[`docs/tutorial/`](./), ready to compile, and every output below is what
the compiler really prints: this page is generated by running them, and
CI fails if it no longer matches.

## 1. A buffer and two calls

```phase
extern fn fill(dst: write buffer<f32, 256> @RAM);
extern fn average(src: read buffer<f32, 256> @RAM) -> f32;

fn main() {
    buffer<f32, 256> samples @RAM;
    fill(samples);
    let mean: f32 = average(samples);
}
```

`buffer<f32, 256> samples @RAM` is 256 floats in ordinary memory, owned
by the CPU — `@RAM` is the buffer's *domain*. `fill` and `average` are
`extern fn`s: functions you write in C. Their signatures tell PHASE what
they do with what you give them: `fill` may `write` its buffer, `average`
only `read`s it.

## 2. Handing a buffer to hardware

A DMA engine copies data into memory while the CPU does something else.
In PHASE, that is a change of owner:

```phase
extern fn average(src: read buffer<f32, 256> @RAM) -> f32;

fn main() {
    buffer<f32, 256> samples @RAM;
    move samples -> @DMA;   // the DMA engine owns it now, and fills it
    sync(samples);          // wait for the transfer: the CPU owns it again
    let mean: f32 = average(samples);
}
```

`move samples -> @DMA` gives the buffer to the DMA engine; `sync(samples)`
waits until the transfer is done and gives it back. In between, the CPU
must not touch it — the engine is still writing. Read it too early:

`2_too_early.phase`, lines 5-7:

```phase
    move samples -> @DMA;
    let mean: f32 = average(samples);   // reads it mid-transfer
    sync(samples);
```

## 3. Across function calls

Real drivers start a transfer in one call and wait for it in another,
doing useful work in between. A parameter can say that a call changes
who owns the buffer: `@RAM -> @DMA` means "give me a CPU buffer; when I
return, the DMA engine has it".

```phase
extern fn start_capture(dst: write buffer<f32, 256> @RAM -> @DMA);
extern fn make_window(w: write buffer<f32, 256> @RAM);
extern fn apply(x: read buffer<f32, 256> @RAM, w: read buffer<f32, 256> @RAM);

fn wait_capture(b: buffer<f32, 256> @DMA -> @RAM) {
    sync(b);
}

fn main() {
    buffer<f32, 256> frame @RAM;
    buffer<f32, 256> window @RAM;
    start_capture(frame);    // frame -> @DMA
    make_window(window);     // CPU work while the transfer runs
    wait_capture(frame);     // frame -> @RAM
    apply(frame, window);
}
```

`@DMA -> @RAM` — that the compiler holds it to. Here it keeps it with
`sync(b)`. Without it:

## 4. Views: read, write, borrow

`read` and `write` on a parameter say what a function does with a
buffer. A *borrow* is a temporary view of a buffer: many read views at
once, or one write view.

```phase
extern fn fill(dst: write buffer<f32, 256> @RAM);
extern fn plot(x: read buffer<f32, 256> @RAM);
extern fn normalize(x: write buffer<f32, 256> @RAM);

fn main() {
    buffer<f32, 256> data @RAM;
    fill(data);
    let view = borrow data read;   // a read-only view
    plot(view);
    release view;                  // done with it
    normalize(data);
}
```

## 5. Streaming: ping-pong buffers in a loop

To stream, keep the engine busy: while the CPU processes one buffer, the
engine fills the other. `swap` trades the two names each time round.

```phase
extern fn start_capture(dst: write buffer<f32, 256> @RAM -> @DMA);
extern fn process(x: read buffer<f32, 256> @RAM);

fn wait_capture(b: buffer<f32, 256> @DMA -> @RAM) {
    sync(b);
}

fn main() {
    buffer<f32, 256> ping @RAM;
    buffer<f32, 256> pong @RAM;
    let n: u32 = 0;

    start_capture(ping);
    while n < 3 {
        wait_capture(ping);    // ping is ready
        start_capture(pong);   // fill pong meanwhile
        process(ping);
        swap ping, pong;       // pong's capture is the next one to wait for
        n = n + 1;
    }
    wait_capture(ping);
}
```

A loop body must leave every buffer the way it found it — that is how one
pass of the checker covers any number of iterations. At the top of each
iteration `ping` is in flight and `pong` is free; `swap` restores exactly
that. Forget it:

## 6. One buffer, two halves: circular DMA

Most microcontroller ADC drivers run the DMA engine in circular mode over
one buffer, forever, with an interrupt when each half is full. The CPU may
only touch the half the engine just finished. `split` makes the halves
two separately owned buffers:

```phase
extern fn start_circular(lo: write buffer<f32, 128> @RAM -> @DMA,
                         hi: write buffer<f32, 128> @RAM -> @DMA);
extern fn wait_half(h: buffer<f32, 128> @DMA -> @RAM);
extern fn requeue(h: write buffer<f32, 128> @RAM -> @DMA);
extern fn stop_circular(lo: buffer<f32, 128> @DMA -> @RAM,
                        hi: buffer<f32, 128> @DMA -> @RAM);
extern fn process(h: read buffer<f32, 128> @RAM);
extern fn summarize(x: read buffer<f32, 256> @RAM);

fn main() {
    buffer<f32, 256> ring @RAM;
    let n: u32 = 0;

    split ring into lo, hi;    // two halves, each tracked on its own
    start_circular(lo, hi);
    while n < 2 {
        wait_half(lo);  process(lo);  requeue(lo);
        wait_half(hi);  process(hi);  requeue(hi);
        n = n + 1;
    }
    stop_circular(lo, hi);
    join lo, hi into ring;     // whole again
    summarize(ring);
}
```

While `ring` is split, it can't be used at all — half of it belongs to
the engine. `join` puts it back together, once both halves are in one
domain again. Processing the wrong half — the classic off-by-one-half
bug — is caught:

## 7. Protocols: typestate

Not every rule is about memory. A packet must be parsed before it is
verified, and verified before it is delivered. A `state` declaration
makes the steps part of the type:

```phase
entity Packet : @RAM {
    len: u32
}

state Packet {
    Raw -> Parsed -> Checked
}

extern fn receive() -> Packet<Raw>;
extern fn parse(p: Packet<Raw>) -> Packet<Parsed>;
extern fn verify(p: Packet<Parsed>) -> Packet<Checked>;
extern fn deliver(p: Packet<Checked>);

fn main() {
    let raw: Packet<Raw> = receive();
    let parsed: Packet<Parsed> = parse(raw);
    let checked: Packet<Checked> = verify(parsed);
    deliver(checked);
}
```

`Packet<Checked>` only comes out of `verify`, so `deliver` can only ever
see a verified packet. Skip a step:

## 8. Hardware registers

Peripherals are driven through memory-mapped registers. Declare a
device's register map once — address, each register's access mode, width
and offset, and its bit fields:

```phase
device Timer @ 0x40000000 {
    LOAD:   read write u32 @ 0x00;
    CTRL:   read write u32 @ 0x04 = 0 { ENABLE: bit 0, PRESCALE: bits 4..=7 }
    STATUS: read u32 @ 0x08 { EXPIRED: bit 0 }
}

fn main() {
    volatile_write(Timer.LOAD, 48000);
    volatile_write(Timer.CTRL.PRESCALE, 15);   // divide by 16
    volatile_write(Timer.CTRL.ENABLE, 1);
    let expired: u32 = volatile_read(Timer.STATUS.EXPIRED);
}
```

`volatile_write(Timer.CTRL.PRESCALE, 15)` changes those four bits and
keeps the rest of `CTRL`. Accesses are `volatile`: the C compiler can't
drop or reorder them. And every access is checked against the map:

A misspelled register or field, reading a write-only register, and a map
with overlapping registers are errors too.

A chip usually has several copies of a peripheral, and every program on
the board needs their maps. Declare a layout once as a `device type`, one
`device` per copy at its address, and keep them in a file of their own
that programs `import`. The repository has one for the board used below,
[`examples/devices/mps2_an385.phase`](../../examples/devices/mps2_an385.phase):
five UARTs and two timers.

```phase

fn send(c: u32) {
    while volatile_read(Uart1.STATE.TXFULL) == 1 {
    }
    volatile_write(Uart1.DATA, c);
}

fn main() {
    volatile_write(Uart1.BAUDDIV.DIV, 16);
    volatile_write(Uart1.CTRL.TX_EN, 1);
    send(79);
    send(75);
    volatile_write(Timer0.RELOAD, 48000);
    volatile_write(Timer0.CTRL.ENABLE, 1);
}
```

Real register maps need a little more. Named values and bit operations
(`&`, `|`, `^`, `<<`, `>>`, `~`) compute what to write — and a computed
value is checked against its field like a literal. Some status bits are
cleared by writing 1 to them (`w1c`): writing one *field* of such a
register reads it and writes the rest back, a 1 for every flag that was
set — clearing interrupts nobody handled:

```phase
device Timer @ 0x40000000 {
    CTRL: read write u32 @ 0x00 = 0 { ENABLE: bit 0, PRESCALE: bits 4..=7 }
    INT:  read write u32 @ 0x0C { DONE: bit 0 w1c, OVERFLOW: bit 1 w1c, IRQ_EN: bit 4 }
}

const DIV_16: u32 = 15;               // the field holds the divider minus one
const ON: u32 = DIV_16 << 4 | 1 << 0;

fn main() {
    volatile_write(Timer.CTRL, ON);
    volatile_write(Timer.INT.IRQ_EN, 1);
}
```

## 9. Interrupts

Hardware doesn't wait to be asked: a timer reaching zero, a UART that
received a byte, a DMA engine that filled half a buffer each raise an
*interrupt*, and the CPU drops what it's doing to run that interrupt's
handler. In PHASE a handler is an `interrupt fn` bound to its IRQ number,
and it tells the rest of the program something happened by raising an
`event`:

```phase
import "../../examples/devices/mps2_an385.phase";

extern fn report(n: u32);

event tick;

interrupt fn on_timer0() @ irq 8 {
    volatile_write(Timer0.INT.PENDING, 1);   // acknowledge
    signal tick;
}

fn main() {
    volatile_write(Timer0.RELOAD, 48000);
    volatile_write(Nvic.ISER, 0x100);        // enable IRQ 8
    volatile_write(Timer0.CTRL, 0x9);        // ENABLE and IRQ_ENABLE
    let n: u32 = 0;
    while n < 3 {
        wait tick;                           // sleep until the handler signals
        report(n);
        n = n + 1;
    }
    volatile_write(Timer0.CTRL.ENABLE, 0);       // stop the timer
}
```

`wait tick` sleeps until a handler signals `tick`, then clears it. A
host build has no timer to interrupt it, so each `wait` runs every
handler once, as if its interrupt had just arrived:

```console
$ phase build --stub-externs --run 9_ticks.phase
OK: built /path/to/phase/build/9_ticks
[stub] report(n: 0)
[stub] report(n: 1)
[stub] report(n: 2)
```

A handler can run between *any* two instructions of `main`. Writing one
field of a register reads the whole register, changes the field and
writes it back — so if a handler writes that register in between, its
write is lost:

`9_lost_write.phase`, lines 5-14:

```phase

    volatile_write(Timer0.INT.PENDING, 1);
    volatile_write(Timer0.CTRL.IRQ_ENABLE, 0);   // one tick only
    signal tick;
}

fn main() {
    volatile_write(Timer0.CTRL, 0x8);
    volatile_write(Timer0.CTRL.ENABLE, 1);       // read, modify, write
    wait tick;
```

### Interrupts that hand over buffers

In section 6 the CPU waited for each half of the circular buffer with a
blocking driver call. On a real chip it's the DMA engine's interrupt
that knows a half is full, so let the handler say so: `wait E for b`
waits for event `E`, and the interrupt that signalled it hands `b` back
to the CPU — like `sync(b)`, completed by the hardware.
`examples/circular_dma.phase` streams this way:

`../../examples/circular_dma.phase`, lines 40-49:

```phase
interrupt fn dma0_irq() @ irq 11 {
    if volatile_read(Dma0.STATUS.HT) == 1 {
        volatile_write(Dma0.CLEAR, 1);
        signal half_done;
    }
    if volatile_read(Dma0.STATUS.TC) == 1 {
        volatile_write(Dma0.CLEAR, 2);
        signal full_done;
    }
}
```

`../../examples/circular_dma.phase`, lines 68-76:

```phase
    while n < 4 {
        wait half_done for lo;  // the engine is filling hi now
        process(lo);
        move lo -> @DMA;        // back to the engine before it wraps around
        wait full_done for hi;  // the engine wrapped around to lo
        process(hi);
        move hi -> @DMA;
        n = n + 1;
    }
```

`b` must be the hardware's when you wait for it, as for `sync`. And
within a function an event always hands back the same buffer: once
`half_done` gives back `lo`, it can't give back `hi` — the half the
engine is still filling:

`9_wrong_half.phase`, lines 17-22:

```phase
    wait half_done for lo;
    process(lo);
    move lo -> @DMA;
    wait half_done for hi;   // should be full_done
    process(hi);
    wait full_done for lo;
```

## 10. Trust, and checking the checker

PHASE can't see inside your C. It trusts that an `extern fn` does what
its signature says: touches only the buffers it is given, doesn't keep
them, writes only through `write` parameters, and really performs the
state change its return type claims. A buggy extern can break any
guarantee — the same contract as `unsafe` code in Rust.

To check PHASE itself, build with `--checked`: every ownership rule is
verified again while the program runs, by a checker that knows nothing
about the analyzer. Accepted programs should never trip it; the project's
fuzzer runs thousands of random programs this way.

```console
$ phase build --checked --stub-externs --run 7_packet.phase
OK: built /path/to/phase/build/7_packet-checked
[stub] receive() -> a new Packet
[stub] parse(p: Packet) -> a new Packet
[stub] verify(p: Packet) -> a new Packet
[stub] deliver(p: Packet)
```
